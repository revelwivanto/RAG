# Dataset Schema

Every dataset lives in `data/` and is produced by `data/generate_synthetic_data.py`,
which imports its formulas from `utils/roi_calc.py`, `utils/procurement_calc.py`
and `utils/rag_metrics.py` — the **same** functions `app.py` calls to
recompute and display things live. There is exactly one implementation of
every formula in this project; no CSV contains a number that was typed by
hand into a spreadsheet.

`data_type` / `status` values used throughout:
- `observed` — real, fetched live from a named source (marketplace listings).
- `observed_external` — a real fact from a cited external source, but not
  BNI-specific (BNI employee count, a public salary benchmark).
- `synthetic` — generated by a seeded random process (seed=42, reproducible),
  not a real transaction.
- `assumption` — an explicit, editable input a human chose; always carries
  a `basis`/`rationale`/`source` explaining *why* that number.
- `calculated` — the output of running code over other rows in `data/`;
  never independently typed.
- `illustrative` — kept only for the two "before/after minutes" inputs that
  cannot be sourced without an actual time-motion study; everything
  *derived* from them (hours/rupiah saved) is `calculated`.
- `regulatory_fact` / `no_regulatory_basis` — verified against a cited
  Indonesian law/regulation, either found or explicitly not found.
- `methodology` — a stated formula or convention, not a business input.

## marketplace_listings.csv (182 rows: 17 observed + 165 synthetic)
17 rows are real Tokopedia listings (`data_type=observed`, `source_url` +
`checked_date` populated); 165 are synthetic, sampled from a price model
calibrated so each (cpu_tier × RAM × storage) combination has enough
listings for defensible statistics.

| Column | Type | Meaning |
|---|---|---|
| listing_id | str | Primary key |
| title, brand, cpu_brand, cpu_tier, cpu_model | str | Listing/spec identity |
| ram_gb, storage_gb | int | Core specs |
| dedicated_gpu, gpu_model | bool/str | Discrete GPU presence/model |
| screen_in, form_factor, condition | float/str | Secondary specs |
| price_rp, orig_price_rp, rating, sold_min | float/int | Commercial signals |
| marketplace, seller, seller_location, source_url, checked_date | str | Provenance |
| is_duplicate_listing, is_bundle, is_promo, missing_spec, is_price_outlier, is_suspicious, listing_status | bool/str | **calculated** by the data-quality pipeline (dedup → outlier IQR test → suspicious test) |
| data_type | str | observed / synthetic |

## procurement_history.csv (620 rows, synthetic)
BNI-side purchase-order history. Price fields use the same base-price model
as marketplace_listings (plus a GPU premium when `dedicated_gpu=True`), so
BNI's "current quote" and the market benchmark are directly comparable.
30 near-duplicate clusters are deliberately seeded (same unit+spec, close
dates) so the split-purchase detector in `utils/governance.py` has real
patterns to find.

## procurement_laptops.csv (4 rows)
BNI's standard laptop specification catalog (`internal_assumption`) — spec_id,
spec_name, cpu_tier, ram_gb, storage_gb, dedicated_gpu, screen_in, form_factor,
typical_business_unit.

## procurement_scenarios.csv (5 rows, `assumption`)
qty_tier, assumed_discount_pct, rationale, source. Feeds both the Procurement
Intelligence volume calculator and the ROI model's `discount_qty_tier` lever.

## assumptions.csv (22 rows — the single register of every input)
assumption_id, category, description, value, status, source, notes. **Read
this file before trusting any dashboard number** — it lists, with sources,
every lever the calculations in `utils/` depend on: PPN rate, procurement
regulation basis, BNI employee count, salary benchmark, work-hours
convention, adoption-rate scenarios, citation-validity priors, RAG
sampling probabilities, and investment-cost components.

Two rows are grounded in real, cited external sources (`status=observed_external`):
- **BNI-EMPLOYEES**: 27,201 — Wikipedia's "Bank Negara Indonesia" infobox,
  which aggregates BNI's own FY2025 company-profile disclosure (BNI itself
  states >27,000 employees as of end-2024).
- **SALARY-COMPLIANCE-ANNUAL**: Rp70,749,733/year — Payscale.com "Average
  Compliance Officer Salary in Indonesia" (crowdsourced/self-reported —
  indicative market benchmark, not BNI-specific, not an authoritative
  official statistic; flagged as such deliberately).

Everything else that feeds a Rupiah figure is an explicit `assumption` with
a stated rationale (device-eligible %, refresh rate, adoption rates,
investment components) — none of them claim to be regulatory or BNI-verified
facts.

## legal_documents.csv (40 rows, synthetic)
Document registry. `TOTAL_DOCS_PROCESSED` in pilot_metrics.csv is literally
`len(legal_documents.csv)` — the KPI equals the row count of this file.

## rag_answers.csv (300 rows, synthetic)
`confidence_score` and `source_type` are **sampled** from documented
probabilities (assumptions.csv: CONFIDENCE-BAND-PROB 75/20/5, SOURCE-TYPE-PROB
70/20/10) via `rng.choice(..., p=[...])` — the aggregate percentages you see
on the dashboard (e.g. 75.7/17.0/7.3) are the *realized output* of that
sampling, not forced to match the input probabilities exactly. `has_citation`
is a Bernoulli draw (97% if grounded, 40% if not).

## citations.csv (deterministic row count under seed=42)
citation_id, answer_id (FK), document_id (FK), chunk_id, page, section,
bbox. `CIT-00001` is the flagship worked example used in the Provenance
Chain visual (matches the original one-pager's example verbatim).

## citation_evaluations.csv (NEW — one row per citation, `calculated`)
citation_id, answer_id, document_id, category, confidence_score,
validity_prob, is_valid, data_type. Built by
`utils/roi_calc.py:build_citation_evaluations()`:
`validity_prob = category_prior + (confidence_score − 0.7) × 0.35`, then
`is_valid = Bernoulli(validity_prob)`. **This is the dataset that makes the
citation-validity percentages real** — open this file to see every
individual simulated evaluation behind the aggregate chart.

## citation_validity_by_category.csv (3 rows, `calculated`)
`= citation_evaluations.groupby("category")["is_valid"].mean() × 100`.
No longer a hand-typed 92/88/80 — whatever this groupby produces is what
ships and what the dashboard shows.

## process_time_comparison.csv (4 rows)
`before_minutes` / `after_minutes` remain `illustrative` — there is no
existing system to time-motion-study yet, so these are a stated hypothesis
to validate during a real pilot, not sourced to a report. `pct_reduction`
is calculated from them. Everything downstream (hours/rupiah saved) is
calculated in `process_annual_volume.csv` and `roi_scenarios.csv`.

## process_annual_volume.csv (NEW, 4 rows, `assumption`)
process_name, estimated_annual_occurrences, basis. Three of the four rows
are scaled directly off actual generated dataset sizes (`len(legal_documents)`,
`len(rag_answers)`, `len(procurement_history)`) rather than an arbitrary
typed count — see the `basis` column for the exact scaling rule used.

## investment_breakdown.csv (NEW, 3 rows, `assumption`)
component, basis, unit_cost_rp, quantity, unit, total_rp. Sums to
`pilot_investment_rp` used everywhere else — change the unit costs here and
every ROI number recomputes.

## roi_scenarios.csv (3 rows, `calculated`)
scenario, adoption_rate, discount_qty_tier, time_savings_benefit_rp,
procurement_savings_benefit_rp, pilot_investment_rp, est_annual_benefit_rp,
roi_x, payback_months. Every numeric column here is the **output** of
`utils/roi_calc.py` functions run against investment_breakdown.csv,
process_time_comparison.csv, process_annual_volume.csv, and the real+
synthetic price benchmark in marketplace_listings.csv / procurement_history.csv.
Note the Conservative scenario's ROI is **negative** (roughly -0.45x) — the
model was not tuned to always look good; at 50% adoption, the benefit
genuinely doesn't cover the investment.

## pilot_metrics.csv (3 rows, `calculated`)
TOTAL_DOCS_PROCESSED = `len(legal_documents)`. RECORDS_SEARCHABLE_TOTAL =
sum of row counts across procurement_history + marketplace_listings +
legal_documents + rag_answers + citations (explicitly labeled "this
prototype dataset," not an enterprise-scale projection). ROI_HEADLINE =
the Base Case `roi_x` from roi_scenarios.csv (no more independent,
unreconciled "3.2x" headline number).

## pilot_ramp_curve.csv (6 rows, `calculated`)
`cumulative_records_searchable` = a logistic ramp
(`utils/roi_calc.py:logistic_ramp`, midpoint week 3.5, steepness 0.9)
converging on RECORDS_SEARCHABLE_TOTAL — computed points, not the
original mockup's hand-picked 30/150/320/490/620/720.

## business_unit_impact.csv (4 rows, `calculated`)
Procurement's row = `procurement_savings_benefit_rp` (Base Case) directly.
The other three units split `time_savings_benefit_rp` (Base Case) in
proportion to each unit's share of `rag_answers.csv` rows — an explicit,
reproducible allocation rule (see `generate_synthetic_data.py`, section 16),
not a hand-picked split. Note Procurement dominates by roughly two orders
of magnitude — a genuine model output, not an error: hardware procurement
at bank-wide volume moves far more Rupiah than incremental admin-time
savings at current adoption assumptions.

## doc_prep_time.csv (3 rows, `illustrative`)
Same caveat as process_time_comparison — a stated hypothesis for Image 1's
chart 1, not sourced to a specific study.

## Adaptation note (scope constraint)
The original 16-graph brief's "Illustrative procurement savings opportunity
by category" spanned Server/Laptop/Printer/Monitor. This build is scoped to
**laptops only**, so that chart's category axis is laptop specification tier
(Entry/Mid/High/Premium) instead, keeping the same Historical vs Current
Quote vs Market Benchmark vs Negotiation Gap structure.
